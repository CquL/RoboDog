消息提供给 106 的 ROS2 Docker 自研算法。

```text
  /x30/body_imu
  /x30/leg_odom
        |
        v
ROS2 自研算法
```

## 3. 架构决定

代码和部署拆成两部分：

```text
105:
  x30_sensor_forwarder_105
  ROS1 C++ 节点
  只订阅，不发布，不调用服务

106:
  x30_livox_ros2_transfer
  x30_sensor_receiver
  ROS2 C++ 节点
  在 Docker 中监听并发布 ROS2 话题
```

跨机数据面不使用 `ros1_bridge`，也不让 Docker 连接 105 的
`ROS_MASTER_URI`。项目定义了轻量、带版本的 TCP 二进制协议：

```text
TCP 56110  PointCloud2
TCP 56111  Imu
TCP 56112  Odometry
```

三个数据流相互独立，避免大点云阻塞 IMU 和里程计。点云队列为
latest-only 深度 1，断线后清空旧数据，不做积压回放。

### 11.1 同机 ROS1 与 Docker ROS2 频率对照

在 106 宿主机直接执行 `rostopic`，验证的是通过 ROS1 网络订阅原厂话题；
发布节点仍运行在 105，不表示传感器驱动运行在 106。随后进入
`x30_ros2_passive` 容器验证转发后的 ROS2 话题。

```text
数据             106 宿主机 ROS1                 Docker ROS2
点云             /lidar_points      约 10.00 Hz  /x30/lidar_points 约 9.1-9.4 Hz
IMU              /imu/data          约 200.33 Hz /x30/body_imu     约 200.34 Hz
腿部里程计       /leg_odom          约 200.00 Hz /x30/leg_odom     约 199.16 Hz
```

点云 ROS2 频率来自仅 8 秒的 Python CLI 短窗口，其中包含 DDS 发现和调度抖动；
接收器同期日志为 `invalid=0`、`sequence_gaps=0`。因此目前没有证据证明 TCP
网络帧发生缺口，但 `sequence_gaps=0` 不能覆盖 105 最新帧队列在发送前主动
替换旧帧的情况。仍需结合 105 日志中的 `dropped` 计数和较长时间运行，再
评价端到端点云吞吐和背压。

当前被动转发器不执行多雷达拼接、外参变换、运动补偿或 LIO。数据链为：

```text
原厂 ROS1 /lidar_points
  -> 105 只读序列化
  -> TCP 56110
  -> 106 反序列化
  -> ROS2 /x30/lidar_points
```

因此 `/x30/lidar_points` 是否属于四雷达合并结果，完全取决于原厂
`/lidar_points` 发布节点。已确认它是单个约 10 Hz 的 `PointCloud2`，字段和
`frame_id=lidar_link` 均被原样保留；仅凭这些信息还不能证明四路外参对齐、
运动补偿或机身坐标配准已经完成。需要继续检查原厂
`/livox_lidar_publisher2` 的启动参数和配置。
