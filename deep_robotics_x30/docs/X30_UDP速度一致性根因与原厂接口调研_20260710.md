更新时间：2026-07-10

## 1. 本次要解决的问题

希望上层调用：

```cpp
RobotVelocityCommand cmd;
cmd.vx = 0.20;
cmd.vy = 0.00;
cmd.omega = 0.00;
robot->writeRobotVelocityCommand(cmd);
```

时，X30 的实际身体速度能够接近：

```text
vx = 0.20 m/s
vy = 0.00 m/s
omega = 0.00 rad/s
```

已有实测却表明，当前后端存在明显非线性：

| 输入 vx | 实际观测 | 结果 |
|---|---:|---|
| `0.01 m/s` | `avg_odom_speed ~= 0.159 m/s` | 明显快于指令 |
| `0.02 m/s` | `avg_odom_speed ~= 0.160 ~ 0.163 m/s` | 与 `0.01` 几乎一样，存在低速平台 |
| `1.00 m/s` 持续 1s | 约 `0.205 ~ 0.215m` | 这是起步加速瞬态，不能当作稳态速度 |

## 2. 核心结论

```text
旧版 DeepRoboticsX30 实现的是“遥控器摇杆轴值后端”，
低速平台来自把 SI 速度误映射成摇杆死区轴值。

2026-07-10 通过原厂 udp_sender 二进制静态分析，已经确定两条真正的速度 UDP：
1. /cmd_vel_corrected -> 103:43893，0x123/0x124/0x122，数值为 SI 速度 * 1000。
2. /cmd_vel -> 105:43897，0x150 + 24 字节，载荷为 vx/vy/omega 三个 double。
```

因此，不能通过调整一个 `max_vx` 修复旧摇杆后端；该后端只保留作手动模式和协议调试。`DeepRoboticsX30` 已新增 `udp_physical` 和 `udp_navigation`，默认选择 `udp_navigation`，上层抽象接口不变。

当前还没有做非零速度实机验证。现阶段只确认“发送封装与原厂一致”，不能提前宣称机器人在所有状态下已经实现严格速度跟踪。

## 3. 三种后端数据流

旧 `udp_axis`：

```text
RobotVelocityCommand(vx, vy, omega)
  -> writeRobotVelocityCommand()
  -> velocityToAxis()/yawRateToAxis()
  -> 3 个整数轴值 UDP 包
  -> 192.168.1.103:43893
  -> X30 运动主机
  -> RL 运动控制器
  -> 实际身体速度
```

当前发送的是 12 字节简单指令：

```cpp
struct CommandHead {
    uint32_t code;
    int32_t value;
    uint32_t type;
};
```

轴指令码：

```text
vx:    0x??010130
vy:    0x??010131
omega: 0x??010135
```

`??=21` 表示遥控终端来源，`??=31` 表示导航/自主模块来源。

新增 `udp_physical`，等价于原厂 `/cmd_vel_corrected` 输出：

```text
vx    -> 0x00000123, int32(vx * 1000)
vy    -> 0x00000124, int32(vy * 1000)
omega -> 0x00000122, int32(omega * 1000)
目标  -> 192.168.1.103:43893
```

新增 `udp_navigation`，等价于原厂 `/cmd_vel` 跨主机传输：

```text
12 字节头：code=0x150, size=24, type=1
24 字节载荷：double vx, double vy, double omega
目标：192.168.1.105:43897
105 udp_receiver -> /cmd_vel -> 地形图修正 -> /cmd_vel_corrected
105 udp_sender -> 0x123/0x124/0x122 -> 192.168.1.103:43893
```

## 4. 已确认的问题环节

### 4.1 把摇杆轴值当成了严格物理速度

本地《绝影 X30 接口规格书》第 11 页明确说明：

```text
轴指令是手柄左右摇杆 X/Y 轴输出的指令。
轴值范围 [-32767, 32767]。
下发频率 50Hz。
```

它不是“包里直接装一个 double 类型 m/s”的高级速度 API。

### 4.2 运动状态与规格书公开映射的适用条件不一致

规格书把 `vx/vy/yaw` 的摇杆映射写在“踏步状态下的轴指令”中。

实测运动时：

```text
/control_mode      = 0   手动模式
/robot_basic_state = 16  RL 状态
/robot_gait_state  = 32  L 行走步态
```

测试前后发送 `start_stop_motion` 后，`basic_state` 仍是 16，没有进入文档里的 4 踏步状态。因此不能认定第 12~13 页的公开公式在 RL 状态中仍是完整闭环语义。

### 4.3 `motion_command_source: navigation` 不等于进入导航模式

当前配置：

```yaml
motion_command_source: "navigation"
configure_non_manual_mode: false
configure_navigation_velocity_source: false
```

它只会把指令码前缀变成 `0x31`，不会自动把机器人切到非手动模式，也不会设置地形图速度源。

实测 `/control_mode=0` 也证实了这一点。

### 4.4 当前适配器只发不收

规格书第 17~20 页给出了 `0x1009 MotionStateData`，200Hz 发布，其中直接包含：

```text
basic_state
gait_state
max_forward_vel
max_backward_vel
leg_odom_pos[3]
leg_odom_vel[3]
```

当前 `DeepRoboticsX30` 没有接收和解析这个状态包，所以不知道：

```text
当前实际步态
当前动态最大速度
实际身体速度
反馈是否超时
运动状态是否允许该指令
```

这个后端尚不具备“速度闭环控制器”的必要输入。

### 4.5 测试程序原来只以 20Hz 发轴值

规格书要求 50Hz，原测试代码是 20Hz。2026-07-10 已把：

```text
robot_test_x30_udp.cpp
robot_test_x30_udp_odom.cpp
```

的持续轴指令更新为 50Hz。这是必要的协议合规修正，但它不会单独消除 RL 低速平台。

### 4.6 侧向和 Yaw 公式仍有待验证差异

本地规格书第 13 页写的侧向分母是 `8554`，而当前代码通过 `32767-24576` 得到 `8191`。文档的范围和分母本身也存在数学上的不一致，所以不应该直接猜一个值覆盖。

Yaw 公式写为：

```text
omega = -axis / 32768, when |axis| >= 28212
```

当前代码却把 `max_omega` 经过死区线性映射，且默认不反相。此处与文档存在实质差异，必须用原厂报文或厂家确认，不应继续猜。

## 5. `max_vx/max_vy/max_omega` 是不是错了

当前：

```yaml
max_vx: 1.0
max_vy: 0.5
max_omega: 1.2
```

这组数据与规格书附录 B 的 `L 行走步态` 最大速度完全一致：

```text
最大前进 1.0 m/s
最大后退 1.0 m/s
最大侧向 0.5 m/s
最大转向 1.2 rad/s
```

因此：

```text
它们不是当前前进低速异常的主要原因。
不要把 max_vx 当作经验增益反复调大/调小。
```

更严谨的实现应该从 `MotionStateData.max_forward_vel` 读取当前实际限制，并区分前进与后退最大速度。

## 6. X30 官方目前有哪些控制接口

### 6.1 X30 对外 UDP 协议

本地《绝影 X30 接口规格书》公开了：

```text
心跳、连接确认
基本状态切换
摇杆轴指令
步态指令
模式切换
状态/里程/关节/传感器数据
```

这是当前我们已经接入的公开底层通道。

### 6.2 X30 原厂 ROS1 速度接口

规格书第 37~39、52 页明确给出了：

```text
/handle_state       手柄速度
/cmd_vel            导航模块物理速度
/cmd_vel_corrected  地形图/碰撞检测修正后的物理速度
```

`/cmd_vel` 和 `/cmd_vel_corrected` 都是 `geometry_msgs/Twist`，其值是 m/s 和 rad/s。这是原厂文档中最明确的高级连续速度接口。

但我们的最终产品不必须依赖 ROS1。可以把原厂 `udp_sender` 当作一次性“协议真值源”，找出它如何把 `Twist` 转成 UDP，然后在我们的 Docker 内直接实现同样的 UDP 封装。

### 6.3 官方 `robotserver_sdk`

云深处公开的 [RobotServer SDK](https://github.com/DeepRoboticsLab/robotserver_sdk/blob/main/README.zh-CN.md) 用于控制和监控导航任务，公开功能主要是：

```text
1002 实时状态
1003 发送导航任务
1004 取消导航任务
1007 查询导航任务状态
```

官方 [API 参考](https://github.com/DeepRoboticsLab/robotserver_sdk/blob/main/docs/zh-CN/api_reference.zh-CN.md) 中没有类似 `Move(vx, vy, omega)` 的连续体速度 API。所以它可以用于导航点任务和业务层状态，不能替代当前 `writeRobotVelocityCommand()` 的实时速度后端。

### 6.4 是否有公开的 X30 MotionSDK

截至 2026-07-10：

```text
官方公开 GitHub 有 Lite3_MotionSDK、Lite3_ROS、sdk_deploy、robotserver_sdk等。
sdk_deploy 公开说明当前支持 M20 和 Lite3。
没有查到公开可下载、明确适用于 X30 的连续体速度 MotionSDK。
```

依据：[DeepRoboticsLab 官方仓库列表](https://github.com/orgs/DeepRoboticsLab/repositories)、[官方下载页](https://www.deeprobotics.us/downloads/)。

这不能证明厂家内部或商业支持没有 X30 SDK。应向技术支持明确索取：

```text
X30 Pro high-level continuous body velocity C++/Python SDK
udp_sender 中 /cmd_vel_corrected 到 192.168.1.103:43893 的报文结构
RL/L 行走步态下的轴值到物理速度语义
0x1009 MotionStateData 的网络端口与 network.toml 配置方式
协议与运动固件版本的兼容性表
```

### 6.5 Lite3 官方代码提供的重要线索

云深处官方 `Lite3_ROS` 的 [`Jetson2Motion.cpp`](https://github.com/DeepRoboticsLab/Lite3_ROS/blob/ros2-foxy/src/transfer/src/Jetson2Motion.cpp) 中，`CmdVelCallback` 并不是把 m/s 先转成摇杆整数，而是把：

```text
linear.x
linear.y
angular.z
```

以 `MotionComplexCMD` 的 `double data` 物理值通过 UDP 发送。

重要边界：

```text
这是 Lite3 的官方代码，不是 X30 协议证据。
绝对不能直接拷贝 Lite3 的指令码给 X30。
```

它只证明一个专业上很重要的可能性：原厂 `udp_sender` 可能使用与摇杆轴值不同的“物理速度复杂 UDP 报文”。必须从 X30 自身的原厂进程抓包确认。

## 7. 推荐的最终架构

我们仍然可以保持“单个 Docker 镜像、不依赖各台机器人 ROS 环境”的目标：

```text
上层导航算法
  -> RobotHardwareInterface
  -> DeepRoboticsX30
  -> udp_navigation: 0x150 + 3 个 double
  -> 192.168.1.105:43897
  -> 原厂地形图/安全修正
  -> 原厂 0x123/0x124/0x122
  -> 192.168.1.103:43893
```

保留三个明确后端：

```text
udp_navigation（默认、推荐）
  用途：自研导航算法输出物理速度，同时保留原厂 105 安全层。
  依赖：X30 原厂 105 感知/地形图链路正在运行。

udp_physical（诊断/备选）
  用途：复刻原厂 /cmd_vel_corrected 到运动主机的物理速度包。
  风险：绕过 105 地形图修正，不作为日常导航默认入口。

udp_axis（兼容旧测试）
  用途：摇杆/手动模式、方向验证、原始协议调试。
  不承诺：vx/vy/omega 与实际 SI 速度严格一致。
```

`RobotHardwareInterface` 的三个抽象函数无需修改。只在 `DeepRoboticsX30` 内部更换后端。

## 8. 原生 UDP 后端应具备的能力

### 8.1 发送和超时停车

```text
writeRobotVelocityCommand()
  校验 NaN/Inf
  按 max_vx/max_vy/max_omega 做安全限幅
  立即按当前 velocity_backend 发送
  记录最后一条非零命令时间

后台看门狗线程
  50Hz 检查
  上层非零命令超过 250ms 没更新 -> 持续发零
  零速度保持 3s 后停止额外发送
```

正式导航仍应以 50Hz 调用统一速度接口。看门狗是算法卡住后的停车兜底，不是正常发送频率的替代品。

### 8.2 状态接收线程

解析 `0x1009 MotionStateData`，并实时维护：

```text
basic_state
gait_state
max_forward_vel/max_backward_vel
leg_odom_pos
leg_odom_vel
last_feedback_time
```

反馈超时、状态不允许运动、速度超限时，底层直接拒绝非零命令并发停止。

### 8.3 不要在每个速度命令前发 toggle

`ACTION_START_STOP_MOTION` 是状态切换指令，不是速度指令。真正导航运行时不应该每次都 toggle。

应改成：

```text
启动阶段检查状态
需要时只切换一次
等待状态反馈确认
然后连续发速度
停止时先发零速度，再按业务需求切状态
```

## 10. 报文分支的最终结果

原厂同时实现两种物理速度封装，不是摇杆轴值映射：

```text
SafeVelocityCallback(/cmd_vel_corrected)
  -> 0x123: int32(linear.x * 1000)
  -> 0x124: int32(linear.y * 1000)
  -> 0x122: int32(angular.z * 1000)
  -> 103:43893

NavVelocityCallback(/cmd_vel)
  -> 0x150, size=24, type=1
  -> double linear.x, double linear.y, double angular.z
  -> 105:43897
```

所以旧 `udp_axis` 的低速平台不需要再做经验比例校正。真正速度后端应直接复刻以上两种原厂封装。

### 15.1 空闲和 `/cmd_vel=0`

`factory_idle`、`factory_cmd_vel_zero`、`factory_cmd_vel_zero_repeat` 三组中，所有 UDP 负载都完全相同：

```text
payload length: 12 bytes
source port: 43229
destination: 192.168.1.103:43893
payload hex: 01 00 04 31  00 00 00 00  00 00 00 00
little-endian words: (0x31040001, 0, 0)
period: about 300.1ms
frequency: about 3.33Hz
```

即这三组中只有：

```text
0x31040001 navigation-source heartbeat
```

当前 `control_mode=0` 时，向 `/cmd_vel` 以 50Hz 发布零速度并没有让原厂 `udp_sender` 产生任何额外运动 UDP 包。

### 15.2 `/cmd_vel_corrected=0`

本组共 1094 个 UDP 包，可精确分为：

```text
38 个心跳包
  source port: 43229
  code: 0x31040001

1056 个速度包
  source port: 50515
  352 个 code 0x00000123
  352 个 code 0x00000124
  352 个 code 0x00000122
```

每个速度周期的报文顺序固定为：

```text
0x123 -> 0x124 -> 0x122
```

三个包在几微秒内连续发出，下一组间隔约 20ms，即原厂按约 50Hz 把每条 `Twist` 拆成三个 UDP 包。

零速度时三种负载分别为：

```text
23 01 00 00  00 00 00 00  00 00 00 00
24 01 00 00  00 00 00 00  00 00 00 00
22 01 00 00  00 00 00 00  00 00 00 00
```

也就是：

```cpp
struct FactoryVelocityPacket {
    uint32_t code;   // 0x122, 0x123 or 0x124
    int32_t value;   // SI velocity multiplied by 1000
    uint32_t type;   // always zero for SendSimpleData
};
```

### 15.3 已确认与尚未确认的边界

已确认：

```text
1. 原厂物理速度路径不使用我们当前的 0x31010130/31/35 摇杆轴指令。
2. 0x123 = linear.x * 1000，int32，截断到零。
3. 0x124 = linear.y * 1000，int32，截断到零。
4. 0x122 = angular.z * 1000，int32，不反号。
5. 原厂发送顺序固定为 0x123 -> 0x124 -> 0x122。
6. 原厂物理速度路径带 250ms 超时停车，并以 50Hz 持续发零约 3s。
7. /cmd_vel 使用 0x150 多数据包，载荷是三个 little-endian double。
8. 105 udp_receiver 收到 0x150 后原样发布 geometry_msgs/Twist。
9. 三个速度包与心跳使用不同的本地 UDP socket。
10. 速度包发送频率约为 50Hz。
```

尚未确认：

```text
1. 运动主机在不同 control_mode/basic_state 下对物理速度包的执行条件。
2. 105 地形图链在当前 APP 导航模式下的完整状态前置条件。
3. 不同 X30 固件版本是否保持完全相同的 UDP ABI。
```
