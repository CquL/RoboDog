## 2. 规格书确认结果

### 2.1 山地步态

规格书第 14 页：

```text
手柄来源指令码：0x21010421
导航/自主模块来源：0x31010421
指令值：无意义
指令类型：0
gait_state：33
```

附录 B 最大速度：

```text
最大前进：1.0 m/s
最大后退：1.0 m/s
最大侧向：0.8 m/s
最大转向：1.2 rad/s
```

山地步态是运动主机步态切换指令，不需要累积帧地形图准备。但规格书要求机器人处于可切换步态的运动状态；切换前应先持续发送零速度，并在切换后确认 `gait_state=33`。

### 2.2 45 度楼梯步态

规格书第 14 页：

```text
手柄来源指令码：0x2101040B
导航/自主模块来源：0x3101040B
指令值：无意义
指令类型：0
gait_state：8
```

附录 B 最大速度：

```text
最大前进：0.3 m/s
最大后退：0.2 m/s
最大侧向：0.2 m/s
最大转向：0.8 rad/s
```

45 度楼梯步态只能在累积帧地形图模式下使用。累积帧模式不支持地形图碰撞检测，因此不能把它当成普通导航步态直接切换。

## 3. 45 度楼梯的完整前置流程

规格书第 28-30 页要求：

```text
1. 机器人完全静止站立。
2. 向 192.168.1.105:60000 发送：
   code=0x0BAA0001, value=1, type=0
   开启激光里程计。
3. 等待同码应答：value=0 表示成功，value=-1 表示失败。
4. 向 192.168.1.105:43899 发送：
   code=0x3101EE01, value=20, type=0
   请求切换累积帧模式。
5. 等待地形图状态：
   code=0x3100EE01, value=18 表示准备中；
   code=0x3100EE01, value=20 表示累积帧已就绪。
6. 准备状态超过 10 秒仍未进入 20，按切换失败处理。
7. 只有确认 value=20 后，才发送 0x3101040B 选择 45 度楼梯步态。
8. 再确认 gait_state=8，之后才允许发送非零速度。
```

退出累积帧模式时：

```text
1. 先发零速度并确认机器人停止。
2. 先把地形图切换到实心/镂空/无踢面模式之一，并确认状态。
3. 再向 192.168.1.105:60000 发送：
   code=0x0BAA0001, value=0, type=0
   关闭激光里程计。
4. 切回普通步态并确认 gait_state。
```

## 4. 统一动作名称

当前已在 `robot_hardware_constant.h/.cpp` 增加三个共享语义名称：

```cpp
extern const std::string ACTION_GAIT_WALK;
extern const std::string ACTION_GAIT_L_WALK;
extern const std::string ACTION_GAIT_MOUNTAIN;
```

对应字符串：

```text
gait_walk
gait_l_walk
gait_mountain
```

`ACTION_GAIT_STAIRS_45` 暂未声明，防止在累积帧地形链和反馈状态机尚未完成时被上层误调用。

这只是扩展统一动作词表，不改变 `RobotHardwareInterface` 的函数签名或对象模型。各机器人适配器只实现自己支持的动作；X30 的实现不会影响宇树和智身的速度、初始化或已有动作路径。

X30 当前对未知动作最终返回 `CMD_SUCCESS`。接入步态时应同时把 X30 的未知动作改为返回 `ERROR_ROBOT_HARDWARE_ACTION_FAILED`，避免上层误认为未支持的步态已经执行成功。其它机器人适配器是否统一增加“不支持动作”返回码可作为独立兼容性改进，不与本次 X30 改动混在一起。

## 5. X30 内部实现

### 5.1 简单步态指令

已在 `include/deep_robotics/x30_udp_protocol.h` 增加：

```cpp
constexpr uint32_t kGaitWalkSuffix = 0x00010300;
constexpr uint32_t kGaitMountainSuffix = 0x00010421;
```

最终指令继续通过：

```cpp
sendMotionCommand(motionCode(suffix));
```

当前 `motion_command_source: navigation` 时，实际得到：

```text
山地步态：0x31010421
45 度楼梯步态：0x3101040B
```

### 5.2 45 度楼梯不能只做简单映射

`writeActionCommand(ACTION_GAIT_STAIRS_45)` 应调用 X30 私有状态机：

```text
stop -> 开激光里程计 -> 累积帧请求 -> 等待 mode=20
     -> 发送 45 度楼梯步态 -> 等待 gait_state=8
```

任一步失败都必须：

```text
持续发送零速度
返回 ERROR_ROBOT_HARDWARE_ACTION_FAILED
不继续发送后续步态指令
```

### 5.3 状态接收是实现前置条件

当前 `DeepRoboticsX30` 主要负责发送，还没有直接解析以下反馈：

```text
0x1009 MotionStateData.gait_state
0x3100EE01 地形图模式状态
0x0BAA0001 激光里程计启停应答
```

因此第一版不能把 `ACTION_GAIT_STAIRS_45` 直接实现为单个 `sendto()`。应先补齐状态接收或明确复用现有 ROS1 状态话题。

长期可迁移方案是让 X30 适配器直接接管 UDP 状态接收。需要注意：原厂 106 上的 `udp_receiver` 当前占用 43897，新的接收器不能在未处理端口所有权冲突时直接绑定同一端口。

## 6. 步态速度安全限制

`max_vx/max_vy/max_omega` 仍作为用户配置的最高安全上限。切换步态后，还要叠加规格书步态上限：

```text
effective_limit = min(configured_limit, gait_limit)
```

X 轴需要区分前进和后退：

```text
山地：前进 1.0，后退 1.0
45 度楼梯：前进 0.3，后退 0.2
```

只有发包成功且状态反馈确认后，才能更新当前步态限幅。外部 APP 改变步态时也必须通过状态反馈同步，不能只依赖本进程记录。

## 10. 45 度楼梯对建图和 ROS2 的影响

### 10.1 不要求预先建立全局导航地图

45 度楼梯步态要求的“累积帧”不是自研 SLAM 使用的全局导航地图，而是 X30 原厂在线维护的局部地形/高度图。两者职责不同：

```text
自研 ROS2 SLAM/导航地图：
  用于定位、全局路径规划、局部避障和生成 vx/vy/omega。

原厂激光里程计 + 累积帧地形图：
  用于给 45 度楼梯步态提供连续的局部地形和落脚信息。
```

因此进入 45 度楼梯前不需要提前保存一张全局地图，但机器人必须静止并在线启动原厂激光里程计，等待原厂累积地形图准备完成。

自研 ROS2 建图可以继续存在，不能直接替代原厂累积帧地形图，除非后续完整复刻原厂 `vmap/gridmap_port` 到运动主机的地形数据协议。该替代方案风险很高，当前不采用。

### 10.2 原厂链路与公开 ROS1 接口

规格书公开了 ROS1 地形图控制和状态接口，例如：

```text
/height_map_mode
/height_map_mode_state
/deeprobotics_local_height_map_mid360/obstacle_pointcloud
```

结合原厂启动文件，当前可确认 105 感知主机运行 `udp_receiver`、`udp_sender`、`app_port` 和 `gridmap_port`，其中 `gridmap_port` 面向 103 运动主机。本地 `gridmap_port` 二进制创建 `GridMapTransfer` 时传入固定端口 `0xC34F`，即 UDP 端口 `49999`。预计完整链路为：

```text
Livox 原始数据
  -> 原厂 ROS1 Livox 驱动
  -> ROS1 点云（已知存在 /lidar_points）
  -> 原厂 fast-lio 激光里程计
  -> 原厂 vmap/局部高度图/累积帧
  -> gridmap_port
  -> 192.168.1.103:49999 运动主机
  -> 45 度楼梯落脚和运动控制
```

`fast-lio/vmap` 的准确订阅话题还需要在机器狗上通过 `rosnode info` 确认，不能仅根据文件名假定 `/x30/points_merged` 可直接替代原厂输入。

本地二进制还显示 `gridmap_port` 不是原始点云转发器：核心类包含 `gridMapCB(sensor_msgs::PointCloud2)`、`constructPackage(std::vector<pcl::PointXYZ>)` 和 `sendPackage()`。2026-07-13 上机取证确认共享库存在于 `/home/ysc/jy_cog/transfer/lib/libgrid_map_transformer.so`，只是尚未复制到本地项目。因此必须先取得并分析该共享库、确认实际运行主机和输入话题，不能把 ROS2 `PointCloud2.data` 原样发送到 `103:49999`。

### 10.3 当前 ROS2 Docker 的直接影响

当前 `x30_livox_ros2_transfer` 使用 ROS2 Humble 原生 Livox 驱动直接占用雷达 UDP 端口。启动前脚本会关闭原厂 ROS1 Livox 和 IMU 接收，避免两个驱动争抢同一端口。

这对普通 ROS2 点云接入没有问题，但对 45 度楼梯是潜在阻断：如果原厂 ROS1 Livox 被关闭，原厂 `fast-lio/vmap` 很可能失去点云输入，累积帧状态会停在 18 或准备失败。

所以不能同时假定以下两件事成立：

```text
1. Docker 原生 ROS2 驱动独占雷达 UDP 数据。
2. 原厂 ROS1 fast-lio/vmap 仍然自动获得完整雷达数据。
```

### 10.4 不使用 ROS bridge 时的目标架构

本项目明确不采用 ROS1/ROS2 点云 bridge，原因是高带宽点云经过 bridge 后的频率和时延不能满足任务要求。应按以下顺序评估两条无 bridge 路线。

#### 路线 A：原始 UDP 数据面复制，保留原厂地形链

优先验证 Livox 组播数据能否由原厂 ROS1 驱动和 Docker ROS2 被动接收器同时消费，或者通过内核网络层将原始雷达 UDP 包低开销复制到 Docker 的备用端口：

```text
Livox 原始 UDP
  ├──> 原厂 ROS1 Livox -> fast-lio -> vmap -> gridmap_port -> 103:49999
  └──> UDP 组播共享/内核包复制 -> Docker ROS2 点云 -> 自研算法
```

这不是 ROS 消息 bridge，不进行 `PointCloud2` 序列化和跨 ROS 中间件转换，理论上可以保留原始报文频率。原厂驱动应作为唯一的雷达配置/控制端，Docker 端只被动接收点数据，避免两套 SDK 同时向雷达下发配置。

当前 ROS2 驱动使用预编译的 `/usr/local/lib/liblivox_lidar_sdk_shared.so` 管理 socket，仓库中没有 SDK 的网络层源码，尚不能确认它是否支持共享组播端口。需要先在零运动条件下验证 `SO_REUSEADDR/SO_REUSEPORT`，不支持时再评估 `AF_PACKET/tc/eBPF` 包复制或增加独立被动解码器。

路线 A 能保留原厂楼梯落脚能力，同时避免点云 bridge，是当前风险最低的目标。

#### 路线 B：Docker 原生实现完整地形链

若路线 A 无法满足频率或部署要求，并继续让 Docker 原生 ROS2 驱动独占四雷达和 IMU，则 45 度楼梯所需的数据链必须在 Docker 内补齐：

```text
四雷达/本体 IMU
  -> Docker 原生 ROS2 驱动
  -> 多雷达时空同步、外参变换和运动补偿
  -> ROS2 激光里程计
  -> ROS2 局部高度图/累积帧地形图
  -> X30 gridmap UDP 封包器
  -> 192.168.1.103:49999
  -> 运动主机楼梯落脚控制

同一份 ROS2 点云/里程计
  -> 自研 SLAM/全局导航/局部规划
  -> RobotHardwareInterface
  -> DeepRoboticsX30
  -> X30 步态、状态和速度 UDP 接口
```

路线 B 需要修改 `x30_livox_ros2_transfer`，但不是只修改当前 `time_window_cloud_merger`。建议在 `ws/src` 中新增独立模块：

```text
x30_lio                    激光里程计和姿态估计
x30_local_terrain_map      局部高度图及累积帧管理
x30_gridmap_sender         兼容 103:49999 的厂家地形数据封包
x30_stair_pipeline_monitor 数据新鲜度、状态和故障监控
```

当前 `time_window_cloud_merger` 只拼接字段格式一致的 `PointCloud2.data`，并修改输出 header；它没有进行激光里程计、逐点运动补偿、落脚平面提取、局部高度图生成或厂家 UDP 封包，因此不能直接承担楼梯数据链。

`robot_hardware` 继续只负责机器人控制协议：开启/关闭激光里程计、地形图模式状态机、步态切换、速度限幅和速度发送。全局/局部建图算法不放进 `robot_hardware`，抽象接口不修改。

在没有厂家 `grid_map_transformer` 源码/SDK、共享库及协议说明前，不能确认自研地形图的语义、坐标系、点顺序和包结构与运动主机一致。第一步应先提取原厂运行时依赖、确认 `gridmap_port` 的输入话题，并抓取 `103:49999` 的只读 UDP 数据进行协议比对；完成前不实现 45 度楼梯非零运动。

### 10.5 进入 45 度楼梯后的安全责任

累积帧模式不支持原厂地形图碰撞检测，但仍用于 45 度楼梯地形/落脚处理。这意味着：

```text
原厂累积帧：负责楼梯局部地形和步态落脚。
自研 ROS2 局部规划：必须负责前方障碍物检测、速度约束和急停。
DeepRoboticsX30：必须确认 mode=20、gait_state=8 后才放行非零速度。
```

进入楼梯模式后应使用独立限幅，最大不超过规格书上限：前进 0.3 m/s、后退 0.2 m/s、侧向 0.2 m/s、转向 0.8 rad/s；首次测试应从零速度和远低于上限的速度开始。

### 10.8 当前双接收方案的准确含义

当前验证的不是“ROS1 收到 UDP 后再复制给 ROS2”，也没有启动任何 ROS 消息 bridge。实际数据来源和接收关系是：

```text
四台 Livox 雷达
  -> 各自发送一份原始 UDP 到 224.1.1.5:56301/56401
  -> Linux 内核组播分发
       ├── 原厂 ROS1 Livox SDK master socket
       └── Docker ROS2 Livox SDK slave socket
```

ROS1 和 ROS2 在这一方案中都直接接收雷达原始 UDP。ROS1 不是中转站，`/lidar_points` 也没有被转成 ROS2 消息。

当前处于“组播共享”验证阶段，尚未实现以下备用方案：

```text
网卡收到 Livox UDP
  -> AF_PACKET/tc/eBPF 在内核入口复制报文
  -> 一份保持给 ROS1
  -> 一份改送 Docker 独立网络命名空间或备用端口
```

目前已确认：

```text
1. 原厂 ROS1 master 持续发布 /lidar_points，约 10 Hz。
2. ROS2 镜像使用 master_sdk=false，不负责配置雷达。
3. ROS2 SDK 能初始化，并能创建四雷达队列。
4. 新 SDK 的 socket 创建代码启用了 SO_REUSEADDR，但没有设置 SO_REUSEPORT。
5. 在自动等待窗口内，ROS2 尚未产生 /livox/lidar 数据回调。
6. 每次失败后 slave 容器均自动删除，ROS1 未中断。
```

前几次失败并非同一个原因：第一次 SDK 能力检查是 `pipefail` 假失败；第二次是 JSON 日志字段不完整；后续才是当前真正的问题，即同机组播已经完成 SDK 初始化，但 ROS2 数据回调没有发生。

`remote/25_diagnose_livox_slave.sh` 用于区分两个分支：

```text
A. 两个 socket 都加入组播且网卡有原始包：继续检查 SDK 每 socket 收包和设备回调映射。
B. slave 没有形成第二个有效组播成员：停止同 namespace 共享，转向独立网络 namespace/IP 或内核复制。
```

只有诊断结果明确后才选择下一种实现，当前不修改 `gridmap_port`，也不让 ROS2 成为第二个雷达 master。

x30_local_terrain_map

x30_gridmap_sender
  输入：兼容原厂语义的地形数据

x30_stair_pipeline_monitor

#### 完全 Docker 最终应关闭什么

完全 Docker 最终运行时，只关闭与新链路冲突的原厂组件，不关闭整套 ROS1：

| 组件 | 完全 Docker 最终状态 | 原因 |
|---|---|---|
| 原厂 ROS1 Livox 驱动 | 关闭 | Docker 作为唯一 Livox master，避免端口和雷达配置冲突 |
| 原厂 ROS1 Yesense 驱动 | 关闭 | Docker 独占 `/dev/ttyS0` |
| 原厂 fast-lio/vmap/高度图链 | 关闭 | 防止旧地形链继续产生或缓存数据 |
| 原厂 gridmap_port | 关闭 | 保证 `103:49999` 只有一个地形数据发送者 |
| roscore 和无关 ROS1 节点 | 保留 | 不应扩大停机范围 |
| udp_receiver/app_port/机器人状态与控制节点 | 暂定保留 | 步态反馈、模式反馈和控制链仍可能依赖它们，需逐项确认 |

现有 `remote/02_factory_livox_off.sh` 和 `remote/11_factory_imu_off.sh` 只处理传感器驱动；它们不会停止 fast-lio、vmap 或 `gridmap_port`。现有恢复脚本 `remote/06_factory_livox_on.sh`、`remote/12_factory_imu_on.sh` 也只恢复传感器。原厂地形链的精确停止与恢复脚本必须等运行节点、启动脚本和依赖关系调查清楚后再写，当前不能使用模糊的 `pkill`。

#### L_walk 自动恢复现象与流程修正

2026-07-13 后续实测发现：程序内发送 `0x31010300` 后可以确认 `gait_state=0`，但测试进程退出、X30 适配器心跳停止后，连续三次只读 `status` 均稳定显示：

```text
/robot_basic_state=16 (RL)
/robot_gait_state=32 (L_walk)
```

这说明当前 APP/原厂控制器会在测试进程释放控制后重新接管，并恢复其基线 `L_walk=32`。因此以下跨进程流程在本机上无效：

```text
单独运行 walk，确认瞬时 gait=0
-> walk 进程退出
-> 再启动 mountain_move
```

`mountain_move` 不再把当前 `gait_state` 限制为 `0` 或 `32`。只要 `/robot_basic_state` 为当前确认可运动的 `4/16`，导航速度后端下 `/control_mode=1`，程序就直接发送山地步态指令，并在同一个进程中执行：

```text
读取当前 gait_state，仅用于记录
-> 持续零速度
-> 请求 mountain=33
-> 确认并保持 gait=33
-> 状态联锁下发送速度
-> 停止
-> 请求 L_walk=32 并确认
```

当前步态不是山地切换的中间状态或前置白名单。若机器人原厂状态机不接受某个来源状态的直接切换，程序会因收不到 `gait_state=33` 而停止，不会放行非零速度。

规格书第 14 页说明机器人处于踏步运动控制状态时可通过步态指令调整步态，并同时列出 `L 行走 0x21010420` 和 `山地 0x21010421`。本测试不改变身体高度或地形图模式，符合规格书关于 L 行走/山地模式期间不得改变这两项设置的限制。

如果原厂控制器在运动阶段把 `gait_state=33` 重新改成 `32`，逐周期状态联锁会在下一速度周期停止发送非零速度。测试进程退出后的只读状态重新显示 `32` 可以视为外部控制器恢复基线；运动阶段必须始终保持并验证 `33`。

本次 `/cmd_vel` 与 `/cmd_vel_corrected` 的 `rostopic echo` 没有捕获到消息，不能据此否定 UDP 链路：测试脉冲只有 0.5 秒，且 `rostopic echo` 只观察 ROS 发布，不直接观察发往 105:43897 的原始 UDP。后续如需定位中间链，应确保监听与运动测试时间重叠，并结合 `rostopic info` 或抓包。

#### 相同低速命令出现一次不动、一次运动

随后连续两次执行相同的 `mountain_move 0.05 0.5`：

第一次：

同一程序、同一速度和同一持续时间得到不同执行结果，说明差异不是 `0x150` 编码或命令参数，而是运行瞬间的外部控制状态。当前最需要区分的是：

```text
1. control_mode 是否在整个发送窗口保持 1。
2. basic_state 是 4（踏步）还是 16（RL）。
3. 105 内部速度源是辅助手柄源 1 还是导航源 2。
4. 105 内部地形/安全链是否临时放行导航速度。
```

本组实测同时推翻了“106 上 `/cmd_vel` 必须出现 0.05 才能证明 0x150 到达 105”的过强判断：机器人发生了实际运动，但 106 上 `/cmd_vel` 与 `/cmd_vel_corrected` 均未捕获消息。因此这两个话题在当前跨主机 ROS 拓扑中不是该原始 UDP 链路的充分或必要观测点。

测试程序已增加 `/control_mode` 订阅和逐周期联锁：非零速度前必须确认 `control_mode=1`，发送过程中一旦变为手动模式或反馈过期立即停止；同时在运动前打印 `control_mode`、`basic_state` 和 `gait_state`，用于继续区分 `basic_state=4/16` 的执行差异。`vel_source_state` 在 106 不可见，仍需通过 105 抓包或后续只读诊断确认。

#### 首版 control_mode 联锁阈值过严

部署增加 `/control_mode` 联锁的版本后，连续三次 `mountain_move 0.05 1.0/2.0` 均在非零速度发送前被预检拒绝。每次拒绝时最新状态值都是：

```text
control_mode=1
basic_state=16
gait_state=33
```

这些值本身满足程序条件，并且程序已经成功从初始 `basic_state=4、gait_state=0/32` 切换到山地状态。失败发生在 1 秒零速度稳定阶段之后，因此根因是至少一个反馈超过统一的 500 ms 新鲜度阈值，而不是机器人拒绝山地命令；本组三次测试均未发送非零速度。

结合实机低频状态反馈现象，统一使用 500 ms 会产生误拒绝。程序调整为：

```text
basic_state/gait_state 新鲜度：2500 ms
control_mode 新鲜度：2500 ms
leg_odom/robot_velocity 传感反馈新鲜度：500 ms
```

预检继续输出 `control_mode`、`basic_state` 和 `gait_state` 当前值，但不逐项打印反馈年龄；新鲜度只作为内部安全判断，避免无必要日志干扰测试阅读。

运动期间如果收到新的 `control_mode=0` 仍会立即触发停止；2500 ms 只用于区分低频正常发布和反馈失联。正常的 50 Hz 速度发送循环不打印逐包日志，只有错误或联锁触发时才打印。该修改需要重新传输、编译后才能验证，旧二进制仍会显示笼统的 `state missing, stale`。

#### mountain_move 时长改为用户输入

原测试程序将持续时间硬限制为 2 秒，因此输入 `3.0` 会直接拒绝。该限制仅存在于测试程序，不存在于 `DeepRoboticsX30::writeRobotVelocityCommand()`；正式导航只要持续调用统一速度接口，就可以持续运动。

测试程序现改为按照命令行 `<duration_s>` 执行，并由 `config.yaml` 提供可调安全上限：

```yaml
mountain_move_max_duration_s: 30.0
```

因此以下命令分别请求 3、5、10 秒：

```bash
./robot_test_x30_gait ../config.yaml mountain_move 0.05 3.0 CONFIRM_MOUNTAIN_MOVE
./robot_test_x30_gait ../config.yaml mountain_move 0.05 5.0 CONFIRM_MOUNTAIN_MOVE
./robot_test_x30_gait ../config.yaml mountain_move 0.05 10.0 CONFIRM_MOUNTAIN_MOVE
```

正常状态下发送循环使用 `steady_clock` 按输入时长结束。安全联锁、ROS 关闭、UDP 失败或状态反馈超时仍可提前停止，不能为了满足时长而绕过。用户需要更大的测试上限时只修改 `mountain_move_max_duration_s`，不需要重新编译；首次长时间验证仍使用 `0.05 m/s`，不得直接使用 `0.5 m/s`。

## 12. gridmap 49999 协议静态分析修正

### 12.1 关键修正：49999 使用 TCP，不是 UDP

2026-07-13 对本地原厂二进制继续静态分析后，确认此前文档中“gridmap UDP 103:49999”的判断不准确。证据如下：

```text
message_transformer_cpp/gridmap_port
  创建 GridMapTransfer("192.168.1.103", 49999)
  核心构包和发送函数位于 libgrid_map_transformer.so

message_transformer_cpp/gridmap_receiver
  创建 TCPServerSocket(49999, 5)
  accept() 后通过 CommunicatingSocket::recv() 接收
  本地二进制未剥离，能够恢复接收和解包流程
```

因此正确链路应写为：

```text
原厂局部地形图
  -> gridmap_port / GridMapTransfer
  -> TCP 192.168.1.103:49999
  -> 运动主机地形接收器
```

本节结论覆盖本文前面所有把 `103:49999` 写成 UDP 的旧判断。Livox 雷达原始数据仍然使用 UDP，两条链路不能混淆。

### 12.3 当前共享库恢复出的 TCP 帧格式

当前 `libgrid_map_transformer.so` 中的发送格式为小端序：

```text
TCP 连接建立后，每帧先发送：
  uint32_t total_pack

随后发送 frame_len 字节：
  uint32_t frame_len             // 当前帧总长度，含本字段
  uint32_t head_id = 12345       // 0x00003039
  uint32_t layer_size = 1
  uint32_t points_size = N * 12

  重复 N 次：
    float x
    float y
    float z

  float time_count_ms            // 首帧 0.1，之后为相邻发送的单调时钟间隔，单位 ms
  uint32_t source_stamp_sec      // PointCloud2 header.stamp.sec
  uint32_t source_stamp_nsec     // PointCloud2 header.stamp.nsec
  uint32_t pack_time_sec         // 构包时 CLOCK_REALTIME
  uint32_t pack_time_nsec
  uint32_t end_id = 54321        // 0x0000D431
```

由构包代码可得：

```text
frame_len = 40 + N * 12
```

当前二进制的 `sendPackage(payload_size)` 计算结果使 `total_pack=1`，然后一次写出完整 `frame_len` 字节；没有在当前发送实现中观察到固定 1024 字节分块。

此前仅根据本地 `gridmap_receiver` 得出的“图层名称 + 方阵矩阵 + positions”格式，与 2026-07-14 取得的真机 `libgrid_map_transformer.so` 不匹配，应视为另一版本或另一测试协议，不能用于实现当前 X30 发送端。

当前实现不存在 `layer_name`、方阵矩阵或 `positions` 数组。协议实现应以真机共享库、105 运行时订阅和 105 到 103 的 TCP 抓包为准。

### 12.6 gridmap_receiver、gridmap_port 与上游地形算法的职责

`gridmap_receiver` 是本地取得的原厂接收/解包参考程序，但它的载荷格式与当前真机共享库不一致，只能继续用于证明厂家曾使用 TCP `49999`，不能作为当前载荷格式依据。

`gridmap_port` 是 105 启动文件中的 ROS1 节点。其当前版本订阅 `/plane_seg/quadrangels`，将 `PointCloud2` 中的 XYZ 点和时间信息封装后通过 TCP 发送；它不执行 LIO，也没有在当前构包函数中生成多层方阵地图。

组件边界不能写成“点云到楼梯落脚全部由 gridmap_port 完成”。当前更合理的边界是：

```text
原厂 Livox/IMU 驱动
  -> 原厂 fast-lio/localization：去畸变、位姿、重力方向
  -> 原厂 vmap/local height map/plane_seg：累积局部地形并提取平面四边形
  -> /plane_seg/quadrangels：平面四边形顶点 PointCloud2
  -> gridmap_port + libgrid_map_transformer.so：转换为 PointXYZ 帧并通过 TCP 发送
  -> 192.168.1.103:49999
```

共享库的构包和发送协议已经基本恢复，但它不等于 fast-lio、local height map 或 plane_seg 源码。即使完全复刻当前 TCP 帧，ROS2 Docker 仍需自行实现或集成 LIO、局部地形图和四边形平面提取模块。

### 12.20 Docker 下各步态对地形图的依赖边界

2026-07-14 使用 Poppler `pdftotext -layout` 并渲染复核接口规格书第 14、28、54
页。规格书明确写的是“各楼梯步态仅能在其对应的地形图模式下使用”，不是所有步态
都必须使用楼梯局部地图。

| 步态 | 指令后缀 | 当前 robot_hardware | 是否要求特定楼梯地形图 |
|---|---:|---|---|
| 行走 | `0x010300` | 已支持 | 否 |
| 斜坡 | `0x010402` | 未映射 | 否 |
| 越障 | `0x010401` | 未映射 | 否 |
| L 行走 | `0x010420` | 已支持 | 否；运行期间不能切身体高度和地形图模式 |
| 山地 | `0x010421` | 已支持并完成真机验证 | 否；运行期间不能切身体高度和地形图模式 |
| 静音 | `0x010422` | 未映射 | 否；运行期间不能切身体高度和地形图模式 |
| 普通楼梯 | `0x010405` | 未开放 | 是；必须匹配实心 3、镂空 4 或无踢面 5 |
| 累积帧楼梯 | `0x01040A` | 未开放 | 是；必须为累积帧 20 |
| 45 度楼梯 | `0x01040B` | 未开放 | 是；必须为累积帧 20，并持续提供局部落脚地形 |

上表只回答“步态切换是否依赖特定楼梯地图”。在辅助或导航模式下，普通步态的速度
仍可经过原厂地形图碰撞检测链。若关闭原厂 ROS1 雷达和 IMU，而 Docker 只完成传感器
接收，则该碰撞检测链没有新鲜地形输入，不能把普通步态“能切换”解释为仍然具备安全
停障能力。

当前 `x30_livox_ros2:jezetek` 默认镜像只运行传感器和点云合成；虽然包含离线
`x30_plane_seg_core`，但尚未包含或启动 `robot_hardware` 控制进程。因此当前步态调用
仍由 106 宿主机上的 `robot_hardware` 完成。后续可以把同一控制库编进 Docker，统一
接口不需要改变。

速度后端还需分开判断：

```text
udp_axis + 手动模式
  -> 可直接控制运动主机，不依赖原厂地形修正
  -> 但没有原厂地图碰撞检测保护

udp_navigation + 导航模式
  -> 速度进入 105 的导航/地形处理链
  -> 原厂地形链没有新鲜输入时，不能保证放行或安全停障
```

因此完全 Docker 的近期可用范围是普通行走、L 行走和山地等内部步态加自研速度与
避障；楼梯相关步态必须等 Docker 地形链和 `103:49999` TCP sender 离线等价验证完成。
